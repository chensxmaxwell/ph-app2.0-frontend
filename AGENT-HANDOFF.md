### Call (shared by Message and Love)

| File | What |
|---|---|
| `src/screens/call/use-voice-call.ts` | The hands-free loop. `phase`: `connecting` → `greeting` (the opener on its way from Ark; mic inert) → `speaking` (the opener) → `listening` (`listenForUtterance`, one utterance at a time) → `thinking` (`completeCompanionChat`, history = chat + `transcript`) → `speaking` (`ttsSpeak` resolves when the utterance ends) → `listening` again. `ready` = connected with the loop stopped: muted, a denied mic permission, or `missing_key`. On mount with `ring` (the default) the call **rings**: `startRingback()` draws this connect's length (uniform 2–5 s), plays a tone of exactly that length and the phase stays `connecting` (`Calling Kevin`, inert mic, no clock) until `finished` settles — `played` (the tone ran its course), `silent` (the player could not play; the line was held for the drawn length, or `RINGBACK_GRACE_MS` past it capped a player that never reported) — then `greetThenListen`: Ark opener with `OPENER_INSTRUCTION` when a key is saved, bounded by `OPENER_TIMEOUT_MS` (6 s — then `localOpener(name)`, since the mic is inert until the line is spoken), else `localOpener(name)`. `hangUp()` and the unmount cleanup (minimize) `cancel()` the ring, so no tone outlives the screen; a `cancelled` end never greets. `ring: false` (restored / re-entered) = no ring, `listening` from the first frame, `ttsStop()` then listen, no opener. `pressMic`: ignored while `connecting` / `greeting` (`micButtonEnabled`); speaking → barge-in (`ttsStop`, listen); listening → mute (`stopVoiceInput`, `ready`); muted / ready / thinking → listen. Every user action bumps a turn token; an async step only applies its result if its token is still current. An empty listen that ran its window is reopened silently; a **stall** — empty within `LISTEN_FAST_EMPTY_MS` of opening, or refused as `unavailable` / `start-failed` — is reopened after `LISTEN_RETRY_DELAY_MS`, and from `LISTEN_MAX_STALLS` in a row the call shows the stall's copy (`LISTEN_UNRESPONSIVE_COPY` or the failure's message) and keeps reopening every `LISTEN_RECOVER_DELAY_MS`, still `listening` — **the loop never stops to wait for a tap** (Maxwell, 1.2 (18)); the notice comes down on its own once a listen runs. 25. **TTS keys are not chat keys.** The Ark key (`LLM_API_KEY`, `ark.cn-beijing.volces.com/api/v3`) authenticates model inference only. Doubao speech (`openspeech.bytedance.com/api/v3/tts/unidirectional`) wants the **豆包语音 console's** API key (`X-Api-Key`, console.volcengine.com/speech/new/setting/apikeys) or a legacy APP ID + Access Token, and the speakers must be enabled on that account (error 45000000 `speaker permission denied` otherwise). Maxwell asked for one credential, so `tts-config.ts` tries the Ark key when nothing else is configured; `speech-engine.ts` drops the cloud for the session after one refusal (401/403) so a wrong key costs one request per launch, and remembers a refused speaker on its own. Either way the reply is still spoken by `PHNative.speak` with an on-device voice of the companion's gender — never silent, never the system default — and since 1.2 (15) ("the voice sounds bad" = he was hearing AVSpeech) **the call says so** (`voiceKeyHint`) whenever no speech-console credential is saved, so the fix is discoverable from the call itself. `speak()` resolves when the utterance ends and `playAudio()` when playback ends; the call loop waits on that, so keep both promises settling on stop / interruption (`finishPendingSpeak` / `finishPendingPlay`). **MiniMax has the same shape of trap twice over:** its key is a *platform* key, and there are two platforms (China `platform.minimaxi.com` → `api.minimaxi.com`, global `platform.minimax.io` → `api.minimax.io`) with separate accounts — a key from one is `1004` / `2049` on the other, so `minimax-tts.ts` tries the second platform when the first refuses and remembers the one that took it; and its audio is **hex**, not base64 (`bytes.fromhex`, never `b64decode` — the latter plays as noise), so `parseMiniMaxResponse` decodes hex and re-encodes base64 for `playAudio`. `1008` (no balance) is treated like a refused key: nothing will play this session, stop asking. Do not send `emotion: "auto"` (documented, refused).

26. **What is said on a call never enters a chat.** TestFlight 1.2 (15): the call's You / Kevin lines showed up in the Message thread afterwards. Both call screens wrote every spoken turn into their store as it happened (`recordCallExchange` on the thread, a `patchChat` append on the Love transcript). Maxwell's rule: the conversation belongs to the call UI only, and hanging up must leave the thread exactly as it was. `useVoiceCall` keeps `transcript` (its own `CallTurn[]`) and grounds the next reply in chat history + that transcript; `recordCallExchange` is deleted and the screens pass no `onExchange`. Do not add a "save call to chat" path without Maxwell asking for it. `__tests__/voice-video-call.test.tsx` compares the thread / Love messages before and after a turn and after hang-up.

27. **A running `AVCaptureSession` is not a painting preview layer.** 1.2 (15): black PiP, no copy, at 00:30 — the JS shows copy for every state but `running`, so it had received `running`; `PHCameraPreviewView` emitted it from `AVCaptureSessionDidStartRunningNotification` while its hand-managed `AVCaptureVideoPreviewLayer` sublayer (frame copied from `self.bounds` in `didMoveToWindow`, i.e. before RN's layout pass, then patched in `layoutSubviews`) painted nothing. Fix: the layer is the view's own backing layer (`+layerClass`), so it is always the view's bounds; the session is handed to the layer on main and configured / started on the session queue (AVCam's shape); `running` means the layer's `previewing` flag (iOS 13+) is YES, which it is only while it renders frames; `DidStopRunning` behind our back reads as `interrupted`; the JS ignores a late `authorized` after `running`. **1.2 (18) answered the open question: Camera / Microphone / Speech all ON in Settings and the PiP still never cleared its copy.** `running` had been hung on **KVO of `previewing`**, and Apple's documentation for `isPreviewing` says to observe the connection's `isEnabled` to see it change — the flag itself is not promised to post. A notification that never comes leaves `running` unsent while the layer is in fact painting, so JS covers a live preview with `Starting camera…` and then `Camera didn't start.` + Retry. Fix: `previewing` is **polled on main** after `startRunning` (0.2 s, `expectFramesFrom:`), KVO kept only as a fast path; a running session that never previews reports which half failed with the layer's size (`Camera is on but not drawing (96×128).`) instead of leaving JS to guess. Not device-verified. What a screenshot now tells you: `Camera didn't start.` = the session never configured or never ran (Console.app, `AVCaptureSession`); `Camera is on but not drawing (W×H, N frames in / no frames in)` = session running, connection active, layer not painting — `no frames in` is the camera pipeline, `N frames in` is the layer; `…has no room to draw` = RN gave the view no size (that was landmine 29 through 1.2 (19)); `Camera is in use by another app or session.` = two sessions on the camera (landmine 28). **1.2 (19) was still 「不行」 with all of this on board: the cause was never the session or the flag but the view's size — landmine 29.**
28. **One `AVCaptureSession` on the camera at a time, and never overlapping.** Two sessions on the same device interrupt each other (`AVCaptureSessionInterruptionReasonVideoDeviceInUseByAnotherClient`) and the one that survives is often black — and `stopRunning` blocks for a good fraction of a second. Every `PHCameraPreviewView` used to own its own serial queue, so a replacement view (PiP Retry remounts through `key={attempt}`, Video toggled off and on, a Message call re-entered) configured and started its session in parallel with the old view's stop. Now all preview views share `PHCameraSessionQueue()`: RN detaches the old view (`stopPreview` dispatches the stop) before it attaches the new one (`configureAndRun` dispatches configure + start), and the serial queue runs them in that order. Keep it that way: never give a view its own queue, never `startRunning` from main. The audio session is not in this picture — the capture session has no audio input and `automaticallyConfiguresApplicationAudioSession = NO`, so PHNative's `Record` / `Measurement` recognizer session and the synthesizer's `Playback` switch cannot pause the camera (video-only sessions do not observe `AVAudioSession`); if the PiP ever reports `Camera paused: the audio device is in use elsewhere.`, someone added an audio input. `usesApplicationAudioSession` is deliberately left at its default: for a video-only session it is inert, and switching it off would make the capture session activate a private audio session, which could interrupt the recognizer's — the one coupling that would actually hurt.
29. **A native view prop must never share its name with a style attribute or an `RCTViewManager` prop.** RN (Paper) flattens `style` and the component's own props into **one** payload for UIManager (`ReactNativeAttributePayload.diffProperties`: a later key overwrites an earlier one), and the base `RCTViewManager` exports Yoga's layout props as shadow props — `position`, `top`, `left`, `width`, `flex`, `display`, `opacity`, `transform`, … are all valid top-level attributes of every native view. `PHCameraPreview` exported the camera side as `position` ("front"), so the PiP's payload carried `position: "front"` instead of the style's `absolute`; `RCTComponentData` applies each key to the view **and** to the shadow view, `RCTConvert YGPositionType` did not know "front" and fell back to `relative` (an `RCTLogInfo` in Debug, silence in Release), and a relative child with no width or height inside the centred PiP frame is 0×0 — an `AVCaptureVideoPreviewLayer` with no bounds paints nothing, whatever the session does. That was the PiP from 1.2 (15) (black, no copy: `running` from `DidStartRunning` over a 0×0 layer) through (18) (KVO never fired on a layer with no bounds) to (19) (polled flag still NO; `Camera is on but has no room to draw.` if he waited 4 s) — three builds spent on the session and the flag while the view had no size. The prop is `facing`. `__tests__/camera-pip-layout.test.tsx` mounts the real `CameraPreview`, runs its host props through RN's own `ReactNativeAttributePayload.create` with the attributes `getNativeComponentAttributes` would build (every `RCT_EXPORT_*_PROPERTY` of `RCTViewManager.m` and of the camera manager, plus `ReactNativeStyleAttributes`) and fails if `position` is not `absolute`, if any camera prop collides, or if the JS passes a prop the manager does not export. Before adding a prop to any native view, check its name against `ReactNativeStyleAttributes` and `RCTViewManager.m`. Not device-verified as of this entry (Jest against RN's real payload code only).
